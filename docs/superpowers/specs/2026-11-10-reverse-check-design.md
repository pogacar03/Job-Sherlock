# 反向背调首版设计

这是实现首版时采用的默认方案，尚不是用户明确选择的技术栈。用户要求参考 GitHub 福尔摩斯项目，了解公司、具体部门的氛围和工作强度，并要求继续开发、暂不进行 brainstorming。

## 目标与范围

交付可运行的本地 Python CLI、仓库内可发现的 Codex Skill，以及中文 HTML / Markdown / JSON 报告。输入公司、部门、业务线、城市、岗位、基准日期；先生成调查问题和检索式，再由使用者或宿主 Agent 读取公开原文、导入证据，最后生成可复查报告。Python 3.11+，运行和测试仅使用标准库。

首版提供工作强度、团队氛围、管理沟通、稳定性、薪酬兑现、成长空间六个维度。检索不是判断：首版不内置登录平台爬虫、不冒充已经完成联网调研；联网采集由 Skill 使用宿主现有搜索工具完成。原文无法获取时仍保存线索，但不将摘要升级为已核实结论。

## 方案选择

1. 纯 Skill：容易开始，但证据校验和去重依赖每次模型执行。
2. **Skill + Python 证据引擎（本次实现）**：保留宿主搜索和多 Agent 能力，关键判断规则可测试、可复现；需要宿主或用户提供原文和结构化提取。
3. 独立 Web 应用和采集后台：能批量调度，但需要搜索服务、密钥、持久化及更多运维。作为后续阶段。

## 证据契约

每条证据包含来源定位、原文文本、原文摘录、转述的观察、来源类型、获取方式、所属公司/部门/城市/岗位/业务线、观察日期、发布日期、获取日期、维度、正负方向和来源血缘 origin_id。摘录必须是保留原文的子串；系统验证这一点不等于验证外部网页真实性。

公司用显式别名匹配；目标填写的部门/城市/岗位/业务线必须逐项匹配。缺失或不同只能作为背景，不能推成目标部门事实。观察日期不明确、超出默认365天窗口、发生在基准日期以后、原文不可见、官方或二手材料均仅作为背景。

可分析证据为匹配范围且近期、有原文的员工自述或用户提供的访谈。对匿名身份和用户提供的来源归属不做真实性认证。相同 origin_id、规范化 URL 或相同摘录组成同一来源簇，按连通分量去重；跨平台或多个 Agent 不增加独立来源数。

不输出公司好坏总分或伪精确概率。每个维度展示未知/存在观察/相互矛盾、来源簇数、原文与观察、背景和缺口。相反方向同时存在则保留分歧，不按票数消除。多来源只是材料覆盖，不是统计置信度或已认证事实。没有证据显示未知。

## 模块与工作流

`casebook` 负责验证与原子写入；`analysis` 负责范围/时间/来源簇/冲突；`report` 输出三种可携带文件；CLI 暴露 init / plan / import / report / demo。初始化和报告默认不覆盖已存在文件，导入任一条错误时整批不写入。

Skill 根据任务规模选择串行或并行：协调者确定对象；员工材料搜集和官方背景搜集可独立进行；登记者提取原文与范围；反证检查者追查转载、时间差与部门差异；最后调用同一个引擎出报告。所有角色共享证据账本，不投票认定事实。

报告包含范围、材料覆盖、六维判断、原文来源、背景、未验证线索、面试核实问题和获取限制。示例使用虚构公司，显著标注演示数据。HTML 无第三方脚本、所有输入转义，来源链接只接受 HTTP(S) 或不可点击的 user-provided 引用。首版报告包含导入文本，适合本地保存，公开分享由使用者另行决定。

## 验收

真实运行 CLI 完成初始化、检索计划、导入、报告；非法引用、批量原子性、转载去重、同部门冲突、时间失效、部门/城市/岗位不匹配、摘要、空材料和 HTML 输入均有行为测试。用离线虚构案例展示工作流；明确未针对某家真实公司完成调查。

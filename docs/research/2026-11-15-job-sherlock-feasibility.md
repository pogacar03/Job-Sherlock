# Job-Sherlock 可行性评估与验证方案

评估日期：2026-11-15（上海）。代码基线：本地 `53d6c87`，GitHub main `f68c08d`；两者 Git tree 同为 `5d03f713ecd5fa92414c6354d53fc520bed23fbf`。本次复查 70 项单元测试全部通过；没有重新登录或扫描论坛。测试通过只说明覆盖到的软件行为符合预期，不证明调查结论准确或平台持续可用。

## 当前判断

值得继续验证的定位是：**围绕一个具体岗位，发现工作强度与团队氛围线索，保留原文、适用范围和分歧，帮助求职者提出有效的核实问题。**

现有代码是可运行的采集与证据整理原型。它尚未证明能够稳定回答任意部门的工作日常，也不足以支持自动公司评分或普遍覆盖的承诺。开源工具的可用性、调查效果和付费产品的成立，需要分别验证。

## 代码与实测支持了什么

| 已核查事实 | 对可行性的意义 |
|---|---|
| `scan` 默认使用小红书、牛客、脉脉，保存正文、部分评论、访问状态与待审阅材料 | 已经超过单纯生成网页搜索词，但各渠道覆盖不完整 |
| 2026-11-11 的特定开发样本中，牛客两篇读取13条可见评论，小红书两篇读取37条顶层/子回复；脉脉打开两条原帖，其中一篇正文可读 | 证明部分真实读取路径可运行，不能估计平台整体成功率或目标证据覆盖率 |
| 该真实案例最终账本只有一条背景材料，符合团队、时间与来源类型要求的证据为零 | 尚未验证调查价值；不等于网上没有证据，也不能把未审阅候选都算作无用 |
| `forums.py` 用公司名/公司别名与工作体验词同时命中筛选，默认查询可能把完整部门缩成英文缩写 | 公司级相关性不能替代部门归属；长部门名、别称和业务层级缺少专门处理 |
| `analysis.py` 依赖已填写的范围、来源类型、观察日期和方向；部门等字段按规范化字符串精确匹配 | 规则可复查，但正确元数据主要依赖采集者；别名容易漏配，手填目标信息也会造成错误归属 |
| `init → scan → 审阅 JSON → import → report`，在线读取另外依赖 OpenCLI、扩展和会话 | 已经是 CLI，但用户完成真实调查的成本高于一条命令 |
| README、旧 `plan` 与 Skill 仍保留部分早期六维描述 | 项目承诺尚未统一到用户指定的工作强度与氛围，需要同步收敛 |

## 数据困难需要分层判断

1. **取得内容。** 登录、渲染、跳转、页面改版、限流、评论分页会影响读取。这一层主要靠适配器、故障分类和持续维护改善；扩展平台不会消除维护成本。
2. **找到目标。** 公司、业务线、部门、子团队、城市、岗位、时间共同决定适用范围。某人提到 CRM，不足以认定属于目标国际化团队；别称映射要保留依据及有效时间。
3. **找到实际体验。** 面经、求助、招聘宣传、转述和亲历体验必须分开。帖子问“能不能做到某种作息”，不能变成该团队实行这一作息的证据。
4. **判断材料能支持多大结论。** 亲历自述也只代表特定作者与时期；匿名身份、转载、组织变动和发帖选择偏差不会因帖子增多自动消失。论坛样本不能直接估计整个部门的加班比例。

数据接入是首要工程瓶颈；近期、同团队、可追溯体验的稀缺性是更深的产品约束。Multi-agent 能分工读取与核验，不能补出不存在或未获访问的事实。

## 与 Sherlock 的对照

Sherlock 的官方使用入口是 `sherlock user123`，输出找到的账号链接；站点规则把用户名映射到候选 URL，再根据响应特征判断是否存在。这个任务可以通过增加或修复单个站点规则持续扩展。它也有误报、封锁和失效规则，命中相同用户名不代表已经验证是同一个人。参见[官方 README](https://github.com/sherlock-project/sherlock/blob/master/docs/README.md)、[核心实现](https://github.com/sherlock-project/sherlock/blob/master/sherlock_project/sherlock.py)、[站点规则](https://github.com/sherlock-project/sherlock/blob/master/sherlock_project/resources/data.json)及[本次独立核查](2026-11-15-sherlock-feasibility.md)。

Job-Sherlock 的输入对象、搜索词和答案都不固定。我们需要先发现讨论，再读取上下文、匹配团队、区分提问与体验、处理日期和矛盾。这比用户名存在性检测多了证据解释与归属环节，不能通过复制 CLI 外观获得同样的可靠性。

对 Sherlock 传播优势的解释属于产品推断：承诺简单、操作短、输出可点击复查、扩展任务适合社区贡献，以及多种分发途径，都有利于被试用和传播。本次没有用户增长研究，不能断言这些因素的因果贡献，也不能用 Star 数替代使用效果或商业收入。

## 建议保留与调整的设计

- **保留 CLI、原文快照、错误状态、来源去重、分歧和未知。** 这些是可复用的基础。
- **先做好三个来源。** 优先补充脉脉评论、已知链接直接读取、评论上下文和日期保留。OfferShow、V2EX 后续接入应由有效线索增量决定。
- **增加可检查的对象匹配。** 从用户提供的 JD 或明确信息建立部门称呼与业务范围；相关公司材料、可能同团队材料、已确认范围材料分别呈现，避免全丢弃或全纳入。
- **把采集结果变成证据卡。** 每条展示原话、作者自述/提问/转述类型、体验时间、团队匹配依据、引用位置与待核实项。让用户直接审阅，减少手工编辑 JSON。
- **用模型辅助提取和追问。** 提取必须指向原文；无法确认的字段留空。强度优先提取下班、夜间响应、周末与值班；氛围优先提取反馈、协作、冲突处理的具体事件。
- **统一调查入口。** 自动检查后端、执行有总预算的扫描、保留部分成功结果、显示覆盖缺口，并提供审阅入口。Skill 负责自然语言编排，CLI 负责可复现的读取与存储。先验证单一流程，暂不把 Agent 数量作为功能目标。

这些是后续设计建议，本次未实现这些新增能力。

## 如何决定继续投入或转型

先建立 **20 个真实求职目标的探索性评测集**，包含讨论丰富、讨论稀少和部门名称含糊的情况；另外保留一组已知原文链接用于判断读取质量。冻结目标、时间窗口、查询预算和版本。人工与工具各使用相同的30分钟研究预算，另行记录首次安装时间；使用互不看对方结果的研究者，再盲审两边候选的合并集合。

| 指标 | 测量方式 |
|---|---|
| 读取成功率 | 已知可访问链接中，正确获取正文及约定评论范围的比例；平台与登录条件分开统计 |
| 线索相关性 | 前10条中真正相关的目标团队线索数；提问和亲历体验分别统计 |
| 有效体验覆盖 | 多少案例获得近期、范围匹配、含具体工作体验的原始自述；记录来源关联，不把多条评论直接当多份独立证据 |
| 提取与归属错误 | 摘录失真、问句当事实、其他团队移用、日期推断等错误逐条复核 |
| 用户成本 | 设置、等待、审阅、纠错分别计时；计算得到可用材料所需的主动操作时间 |
| 维护成本 | 在后续重复核查中记录适配器失效次数、修复工时与实际新增有效材料 |

合并候选不是全网真值，只能作为有限参考集；不把相对参考集的发现率写成全网召回率。20例也不足以证明普遍适用。

可事先约定一个探索性继续投入门槛，例如：在人工确实能找到有效体验的案例中，工具有至少70%也能找到一条符合条件的体验，用户主动操作时间中位数减少至少30%，展示为体验的内容均能定位原文，并且本轮审阅未发现跨团队归因或问句事实化。数字是项目决策假设，不是已达成指标、行业标准或统计可靠性保证；还须同时报告全部20例的覆盖，不能只挑有数据的子集展示。

按失败原因决定方向：

- **人工能找到、程序找不到：** 继续改善别称、检索和评论读取，属于工程缺口。
- **人工也长期找不到目标团队体验：** 把主交付转为“面试尽调与求证助手”，让公开线索帮助生成针对性问题，并整理用户自己取得的面试回答、访谈笔记和相互矛盾之处。
- **材料能找到、用户仍没有省时：** 优先重做审阅与输出流程。
- **工具有用、付费需求尚弱：** 先维持开源 CLI + Skill；付费可行性另用真实用户行为验证。
